Part 2: a boundary around native commands

A native sandbox is an operating-system restriction applied to a process and its children. These rules constrain commands independently of whether a command hook is trusted.

Illustration only. The measured result is narrower than “every Codex tool is isolated.”

Controls

The test could detect a leak

Unrestricted access succeeded. Removing the denies made the negative test fail under otherwise identical managed-policy arguments.

Native cases included direct reads, shell commands, xargs, child processes, symlinks, deep paths, and a newly created matching path. No real credentials were used.

Unverified: fresh desktop sessions, product structured-read tools, browser/MCP access, escalated execution, and Linux/Windows native enforcement. Gemini does not support this path boundary; Claude retains its own renderer.

The aggregate repository gate had one independently reproduced base-branch failure. Its focused rerun passed, as did remaining available gate components. That aggregate run is still recorded as failed.

A path list protects only the names it covers. It does not discover every secret, remove secrets already in process environment variables, or prevent data copied into ordinary source from being read.

Part 3: move the test workload into a disposable box

The goal is to let the app and browser talk to each other locally without giving their test code access to host services or credentials. This is a proposed workflow, not a delivered capability.

1 · Stage source

Host → filtered snapshot

A trusted launcher stages needed files under verified native credential denial. Reject links and special files; exclude credentials, host caches, and Git metadata.

2 · Execute tests

Snapshot → offline container

Copy the read-only snapshot into disposable working storage. App and browser share container-local localhost. No host ports, host home, credential mounts, or Docker socket.

3 · Collect evidence

Container → validated results

Export bounded results and screenshots through a dedicated output. Clean up owned resources. Source changes do not automatically return to the host.

Image preparation needs separate authorization. Routine runs use the already prepared image offline. Fewer approval interruptions are a goal to verify, not a benefit already delivered.

How this relates to containers, VMs, and Kubernetes

These are different layers, not a universal security ranking
LayerWhat it contributesWhere this work stands
Native process sandboxRestricts selected processes on the host.Part 2 adds known credential denies; verified scope is macOS commands.
Disposable containerSeparates a workload’s files/processes/network through its runtime and configuration.Part 3 proposes an offline app/browser workload. It does not move the entire Codex agent into the container.
Virtual machine (VM)Runs a guest operating system with its own kernel. Shared folders, credentials and network still need deliberate limits.No VM runner is implemented or selected by this plan.
KubernetesSchedules and manages container workloads. Isolation depends on runtime, policy, mounts, credentials and network configuration.No cluster is required by either part. A cluster alone would not close the tool-boundary gaps.

Direction: yes, toward isolating more execution. First protect known credential files; next isolate one complete test workflow. Running the whole agent in a disposable VM/container would be a further design decision covering model access, Git, dependencies, secrets, connectors, and review of returned changes.
